Integration Team Metrics: Modifying Alerts & Dashboards

A Practical Guide for Engineers

This guide will help you understand how to modify existing metrics, update dashboards, and test changes in the Konflux observability infrastructure. Learn by doing - each section focuses on practical tasks with embedded concepts.

1. Modifying Alerts in the o11y Repository

Alerts notify the team when something goes wrong in Konflux. As an engineer, you'll often need to modify existing alerts - changing their severity, updating thresholds, or adjusting when they fire. This section teaches you how to make these changes safely.

What Alerts Are and Why We Modify Them

Alerts are rules defined in YAML files that monitor metrics. When a metric crosses a threshold (e.g., availability drops below 99%), the alert fires and sends a notification. We modify alerts to:

  • Adjust sensitivity (change thresholds to reduce false positives)
  • Change severity levels (downgrade from critical to warning if not paging-worthy)
  • Update SLO status (control whether the alert pages SRE or just notifies the team)
  • Fix bugs in PromQL expressions

File Locations

Alerts live in the redhat-appstudio/o11y repository:

  • rhobs/alerting/data_plane/prometheus.*_alerts.yaml - Alert rules for the data plane
  • rhobs/recording/*.yaml - Recording rules (pre-computed metrics used by alerts)
# Clone the repo
git clone https://github.com/redhat-appstudio/o11y.git

# Navigate to alerts
cd rhobs/alerting/data_plane/

# List alert files
ls -la prometheus.*_alerts.yaml

Understanding Alert Structure

Here's the anatomy of an alert definition in YAML:

- alert: IntegrationServiceAvailabilitySLOViolation
  expr: |
    (
      avg_over_time(redhat_appstudio_integrationservice_global_github_app_available[24h]) * 100
    ) < 99
  for: 10m
  labels:
    severity: warning
    slo: "false"
  annotations:
    summary: "Integration Service GitHub App availability below SLO"
    description: "Availability is {{ $value }}%, below the 99% threshold"
    alert_routing_key: "integration-service"

Key Fields:

  • alert - Unique alert name (must be descriptive)
  • expr - PromQL expression that triggers the alert when true
  • for - How long the condition must be true before firing (prevents flapping)
  • labels.severity - critical, warning, or info
  • labels.slo - "true" pages SRE, "false" notifies team only
  • annotations - Human-readable descriptions (support template variables like {{ $value }})
  • alert_routing_key - Where to route when slo: "false" (replaces alert_team_handle)
  • alert_team_handle - SRE team handle when slo: "true"

Common Modifications

Changing Severity Levels

Severity controls urgency:

  • critical - Production outage, immediate response needed
  • warning - Issue that needs attention but not immediate
  • info - Informational, for awareness only

When changing from critical to warning, you must also update the slo label and routing field:

⚠️ Important Gotcha

Changing severity from critical (SLO alert) to warning requires THREE changes:

  1. Set severity: warning
  2. Set slo: "false"
  3. Change alert_team_handle to alert_routing_key

Missing any of these will cause deployment failures or incorrect routing.

Updating SLO Status

The slo label controls whether an alert pages the SRE team on-call:

  • slo: "true" - Alert violates an SLO, pages SRE immediately
  • slo: "false" - Alert is important but not SLO-breaking, routes to team only

Modifying Thresholds and PromQL Expressions

Example: Changing availability threshold from 99% to 98%:

# Before
expr: |
  (
    avg_over_time(redhat_appstudio_integrationservice_global_github_app_available[24h]) * 100
  ) < 99

# After
expr: |
  (
    avg_over_time(redhat_appstudio_integrationservice_global_github_app_available[24h]) * 100
  ) < 98

Real-World Example

Let's walk through a real modification: downgrading IntegrationServiceAvailabilitySLOViolation from critical (SLO) to warning.

Before:

- alert: IntegrationServiceAvailabilitySLOViolation
  expr: |
    (
      avg_over_time(redhat_appstudio_integrationservice_global_github_app_available[24h]) * 100
    ) < 99
  for: 10m
  labels:
    severity: critical
    slo: "true"
  annotations:
    summary: "Integration Service GitHub App availability below SLO"
    description: "Availability is {{ $value }}%, below the 99% threshold"
    alert_team_handle: "integration-service-sre"

After:

- alert: IntegrationServiceAvailabilitySLOViolation
  expr: |
    (
      avg_over_time(redhat_appstudio_integrationservice_global_github_app_available[24h]) * 100
    ) < 99
  for: 10m
  labels:
    severity: warning
    slo: "false"
  annotations:
    summary: "Integration Service GitHub App availability below SLO"
    description: "Availability is {{ $value }}%, below the 99% threshold"
    alert_routing_key: "integration-service"

What Changed:

  1. severity: critical → severity: warning
  2. slo: "true" → slo: "false"
  3. alert_team_handle: "integration-service-sre" → alert_routing_key: "integration-service"

Why: The team decided this alert doesn't warrant waking up SRE in the middle of the night. It's important but can wait until business hours.

Updating Alert and Recording Rule Tests

When you modify alerts or recording rules, you may need to update their corresponding tests. Tests validate that your PromQL expressions work correctly and that alerts fire at the right thresholds.

Test File Locations

Tests live alongside the rules they validate:

  • Alert tests: test/promql/tests/data_plane/ (~52 test files)
  • Recording rule tests: test/promql/tests/recording/ (~25 test files)

Naming Convention

Test files follow a predictable naming pattern:

  • Alert file: rhobs/alerting/data_plane/prometheus.integration_service_availability_alerts.yaml
  • Test file: test/promql/tests/data_plane/integration_service_availability_test.yaml

When to Update Tests

You must update tests when you change:

  • Alert thresholds - If you change a percentage from 99% to 98%, update test expectations
  • Time windows - If you change for: 5m to for: 10m, update test timing
  • PromQL expressions - If the metric or calculation changes, update test inputs/outputs
  • Label filters - If you add/remove label selectors, update test series labels
⚠️ Tests Prevent Broken Alerts

If you change an alert threshold but don't update the test, the test will fail in CI. This catches mistakes before they reach production. Always update tests when you modify alert logic.

ℹ️ Don't Forget the SOP

When you change alert thresholds (for: duration, percentages, etc.), you must also update the corresponding SOP to reflect the new values. If your alert now fires after 10 minutes instead of 5 minutes, the SOP runbook should document the correct threshold. See Section 2: Standard Operating Procedures for more details on updating SOPs.

Alert Test Structure

Alert tests simulate time-series data and verify that alerts fire (or don't fire) at the correct thresholds. Here's an example structure:

evaluation_interval: 1m

rule_files:
  - prometheus.integration_service_availability_alerts.yaml

tests:
  # Test 1: Downtime exceeds threshold - alert SHOULD fire
  - interval: 1m
    input_series:
      - series: 'konflux_up{service="integration-service", check="replicas-available"}'
        values: '1x1434 0x6'  # 6 minutes down
    alert_rule_test:
      - eval_time: 1440m
        alertname: IntegrationServiceAvailabilitySLOViolation
        exp_alerts:
          - exp_labels:
              severity: critical
              slo: "true"

  # Test 2: Downtime below threshold - alert should NOT fire
  - interval: 1m
    input_series:
      - series: 'konflux_up{service="integration-service", check="replicas-available"}'
        values: '1x1436 0x4'  # Only 4 minutes down
    alert_rule_test:
      - eval_time: 1440m
        alertname: IntegrationServiceAvailabilitySLOViolation
        exp_alerts: []  # No alert expected

Key points:

  • input_series - Simulates metric values over time (1x1434 = value 1 for 1434 minutes)
  • eval_time - When to check if the alert fired
  • exp_alerts - Expected alerts at evaluation time (empty array = no alert)
  • Tests validate boundary conditions (just over and just under threshold)

Recording Rule Test Structure

Recording rule tests verify that PromQL expressions produce the expected output metrics:

evaluation_interval: 1m

rule_files:
  - integration_service_availability_recording_rules.yaml

tests:
  - interval: 1m
    input_series:
      # Service is available (1 replica spec, 1 replica available)
      - series: 'kube_deployment_spec_replicas{namespace="integration-service", deployment="my-service"}'
        values: '1 1 1 1 1'
      - series: 'kube_deployment_status_replicas_available{namespace="integration-service", deployment="my-service"}'
        values: '1 1 1 1 1'

    promql_expr_test:
      - expr: konflux_up
        eval_time: 5m
        exp_samples:
          - labels: 'konflux_up{service="my-service", check="replicas-available"}'
            value: 1  # Expect value 1 (available)

Key points:

  • promql_expr_test - Tests the output of the recording rule expression
  • exp_samples - Expected metric values with their labels
  • Tests verify the PromQL calculation produces correct results
ℹ️ Not All Alerts Have Recording Rules

Recording rules are used to pre-compute expensive or complex queries, reducing the computational cost when alerts evaluate. We typically use recording rules for:

  • Availability metrics - Like konflux_up and image-rbac-proxy availability calculations
  • Complex aggregations - Queries that would be expensive to run every time an alert evaluates

However, not all SLO alerts need recording rules. Many alerts query metrics directly if the query is simple enough. The decision depends on computational cost and query complexity. If you're modifying an alert that doesn't have a corresponding recording rule, you only need to update the alert test - there's no recording rule test to update.

Example: Updating Tests After Changing Alert Threshold

Let's say you change an alert's for: duration from 5 minutes to 10 minutes:

Step 1: Update the alert

# Before
for: 5m

# After
for: 10m

Step 2: Update the test

You need to adjust test scenarios to match the new threshold:

# OLD TEST: 6 minutes down triggers alert (threshold was 5m)
values: '1x1434 0x6'  # 6 minutes down - SHOULD fire

# NEW TEST: 11 minutes down triggers alert (threshold is now 10m)
values: '1x1428 0x12'  # 12 minutes down - SHOULD fire

# Also update the "just under threshold" test:
# OLD: 4 minutes should NOT fire
values: '1x1436 0x4'

# NEW: 9 minutes should NOT fire
values: '1x1431 0x9'

Step 3: Run tests locally

After updating, run the test suite (see Section 4: Testing Changes) to verify your changes work correctly.

ℹ️ Test File Reference

Each test file references its corresponding alert or recording rule file using the rule_files: field. This tells the test runner which YAML file to load for validation.

2. Standard Operating Procedures (SOPs)

Standard Operating Procedures (SOPs) are runbooks that guide the team through responding to alerts and incidents. When an alert fires, the SOP provides step-by-step instructions for diagnosing and resolving the issue. This section explains what SOPs are, where to find them, and how they connect to alerts.

What Are SOPs?

An SOP (Standard Operating Procedure) is a documented procedure that describes how to respond to a specific situation. In the context of Konflux metrics and alerts:

  • SOPs provide actionable steps - They tell you exactly what to do when an alert fires
  • SOPs reduce response time - Clear instructions mean faster resolution
  • SOPs enable self-service - SREs can often resolve issues without waiting for the dev team
  • SOPs ensure consistency - Everyone follows the same procedure

Two Categories of SOPs

SOPs are organized into two main categories based on who uses them:

SRE SOPs (SLO Alerts)

Located in: sop/integration-service/SRE/

These SOPs are used by SRE (Site Reliability Engineering) when critical alerts fire. Characteristics:

  • Linked to SLO alerts - Triggered when slo: "true" alerts fire
  • Must have actionable steps - SRE must be able to diagnose and ideally resolve without dev team
  • Linked via runbook_url - The alert YAML includes a runbook_url annotation pointing to the SOP
  • Critical for on-call - These are used during incidents, often outside business hours

Team SOPs (Non-SLO)

Located in: sop/integration-service/ (outside the SRE folder)

These SOPs are for the development team's use. Characteristics:

  • Internal procedures - How the team handles specific situations
  • May be less time-critical - Not used for middle-of-the-night pages
  • Broader scope - Can cover operational tasks, not just alerts

Where SOPs Are Located

Repository: gitlab.cee.redhat.com/konflux/docs/sop

Directory structure:

sop/
└── integration-service/
    ├── SRE/                    # SOPs for SRE on-call (SLO alerts)
    │   ├── alert-name-1.md
    │   ├── alert-name-2.md
    │   └── ...
    └── team-procedure-1.md     # Team SOPs (non-SLO)
    └── team-procedure-2.md
    └── ...

How SOPs Link to Alerts

For SLO alerts (slo: "true"), the alert YAML file includes a runbook_url annotation that points to the SOP:

- alert: IntegrationServiceAvailabilitySLOViolation
  expr: |
    (
      avg_over_time(redhat_appstudio_integrationservice_global_github_app_available[24h]) * 100
    ) < 99
  for: 10m
  labels:
    severity: critical
    slo: "true"
  annotations:
    summary: "Integration Service GitHub App availability below SLO"
    description: "Availability is {{ $value }}%, below the 99% threshold"
    runbook_url: "https://gitlab.cee.redhat.com/konflux/docs/sop/-/blob/main/integration-service/SRE/IntegrationServiceAvailabilitySLOViolation.md"
    alert_team_handle: "integration-service-sre"

When the alert fires, the runbook_url is displayed in the alert notification, giving SRE immediate access to the response procedure.

Working with SOPs

As an engineer, you'll typically interact with SOPs in these scenarios:

Editing an Existing SOP

When you modify an alert or fix a recurring issue, you may need to update the corresponding SOP:

  • Update steps if the resolution procedure changes
  • Add new diagnostic commands based on lessons learned
  • Clarify ambiguous instructions
  • Update links to dashboards or tools

Creating a New SOP

When creating a new SLO alert, write the SOP first, then link it in the alert PR. This ensures:

  • The runbook_url points to a real document when the alert goes live
  • SRE can respond immediately if the alert fires
  • You've thought through the response procedure before the alert exists
ℹ️ Using Existing SOPs as Templates

There's no formal SOP template, but all existing SOPs follow a similar structure. When creating a new SOP, browse the SRE/ folder and use an existing one as a guide for layout and sections.

SOP Review and Approval

SOP changes follow a review process:

  • Approvers: One Integration Service team member + one SRE
  • SRE review focus: Ensuring steps are actionable and SRE can resolve without dev team
  • Tagging SRE: SRE team members like to be explicitly tagged on MRs to review new/updated SOPs
⚠️ Important: Actionable Steps Required

SRE SOPs must have actionable, specific steps. Vague instructions like "check the logs" aren't enough. Specify:

  • Exact commands to run
  • What output to look for
  • How to determine if the issue is resolved
  • When to escalate to the dev team

Common SOP Workflow

Here's the typical workflow when working with alerts and SOPs:

When editing an existing alert:

  1. Make your alert changes in the o11y repository
  2. If the alert behavior changes, update the linked SOP
  3. Submit both changes (alert + SOP) for review
  4. Tag an SRE team member if the SOP changes

When creating a new SLO alert:

  1. First: Write the SOP with clear actionable steps
  2. Submit the SOP for review and merge it
  3. Then: Create the alert with runbook_url pointing to the merged SOP
  4. Submit the alert PR with the SOP link already working
ℹ️ Browse the SOP Repository

The best way to understand SOPs is to read a few examples. Visit the SOP repository and browse the SRE/ folder to see real runbooks.

3. Updating Grafana Dashboards

Grafana dashboards visualize metrics and SLOs. You'll update dashboards to add new panels, fix queries, or change visualizations. The recommended approach is to edit dashboards in the Grafana UI, export the JSON, and save it to the repository.

Where Dashboards Are Defined

Dashboards have two locations:

  • Source repository - Where dashboard JSON lives:
    • redhat-appstudio/o11y/dashboards/ - All Integration Service dashboards
  • Deployment configuration - References which commit to deploy:
    • app-interface/data/services/stonesoup/cicd/saas-stonesoup-dashboards.yml (GitLab internal)

Dashboard Development Workflow

The recommended workflow is to edit dashboards in the Grafana UI, then export the JSON to the repository. This is much easier than editing JSON files directly.

  1. Edit the dashboard in Grafana - Make changes using Grafana's visual editor
  2. Export the JSON model - Go to Settings → JSON Model and copy the complete JSON
  3. Update the repository - Paste the JSON into the dashboard file in redhat-appstudio/o11y
  4. Commit and merge - Push changes to the o11y repository
  5. Update app-interface - Update the commit SHA in saas-stonesoup-dashboards.yml
  6. Changes deploy automatically - Once the app-interface MR merges
ℹ️ Why Edit in Grafana UI?

Editing dashboards in the Grafana UI is much easier than manually editing JSON. You can see your changes immediately, use Grafana's panel editors, and preview queries. Once you're happy with the changes, export the JSON and save it to the repository.

4. Testing Changes

Before your alerts or dashboards go to production, you need to test them. Testing validates that your PromQL expressions work correctly and that your configuration doesn't break existing functionality. This section covers how to run the Konflux test suite locally.

Why Test Your Changes

Testing is critical because:

  • PromQL syntax errors - A typo in your expression will cause the entire alert or dashboard to fail
  • Logic bugs - Your expression might compile but return unexpected results
  • Performance issues - Inefficient queries can overload Prometheus
  • Breaking changes - You might accidentally remove a recording rule that other alerts depend on
  • Catching issues before production - Tests prevent fire-fighting in production

The Konflux observability infrastructure includes automated test suites that validate your changes before they go live. You can run these tests locally on your machine.

Setting Up Podman

Tests run in containers using Podman. If you don't have Podman installed, you'll need to set it up first.

Install Podman (if needed)

On macOS:

brew install podman

On Linux (Fedora/RHEL):

sudo dnf install podman

Initialize and Start Podman Machine (macOS only)

⚠️ macOS Required Setup

On macOS, Podman requires a virtual machine. If Podman Desktop is running, you can skip this step. Otherwise:

# Create the VM (only once, on first setup)
podman machine init

# Start the VM before running tests
podman machine start

You only need to run podman machine init once. After that, use podman machine start before each session.

Running Tests Locally

The test suite uses a container image that checks your PromQL syntax and validates alerting rules. There are separate tests for data plane alerts and recording rules.

Test Data Plane Alerts

Data plane alerts monitor core Konflux services:

cd /path/to/o11y  # Clone of redhat-appstudio/o11y

podman run \
  -v "$(pwd):/work" \
  -w /work \
  quay.io/rhobs/obsctl-reloader-rules-checker:latest \
  -t rhtap \
  -d rhobs/alerting/data_plane \
  -y -p \
  --tests-dir test/promql/tests/data_plane

Test Recording Rules

Recording rules pre-compute expensive metrics:

cd /path/to/o11y

podman run \
  -v "$(pwd):/work" \
  -w /work \
  quay.io/rhobs/obsctl-reloader-rules-checker:latest \
  -t rhtap \
  -d rhobs/recording \
  -y -p \
  --tests-dir test/promql/tests/recording

Replace /path/to/o11y with your local clone of redhat-appstudio/o11y.

ℹ️ Container Image Details

The image quay.io/rhobs/obsctl-reloader-rules-checker is maintained by the RHOBS team. It contains validators for PromQL syntax, rule structure, and test execution.

Understanding Test Output

Successful test runs show output like:

✓ Validating prometheus rules...
✓ All PromQL expressions are valid
✓ Running test suite...
✓ 47/47 tests passed

Test Results:
  Data Plane Alerts: PASS
  Recording Rules: PASS

Errors: 0
Warnings: 0

Key indicators:

  • ✓ checks pass - Your changes are valid
  • ✗ checks fail - Fix the issues before committing
  • Errors: 0 - No syntax or logic errors
  • Warnings: 0 - No issues flagged by validators

Common Test Failures and Fixes

PromQL Syntax Errors

Error:

ERROR: parse error at char 42: unexpected token ")"
❌ Common Cause: Missing or Extra Parentheses

Check your PromQL expression for balanced parentheses. Example:

# WRONG: Missing closing paren
(avg_over_time(metric[5m]

# CORRECT
(avg_over_time(metric[5m]))

Undefined Metrics

Error:

Understanding Observability & SLOs

Observability is the practice of understanding system behavior by examining its outputs. The three pillars of observability are:

1. Metrics

Quantitative measurements of system behavior. Examples:

  • Request latency - How long requests take to complete
  • Error rate - Percentage of failed requests
  • Throughput - Requests per second the system handles
  • Resource utilization - CPU, memory, disk usage

In Konflux, we use Prometheus to collect and store metrics. PromQL is the language we use to query these metrics.

2. Logs

Detailed event records from applications. Logs capture:

  • Errors and warnings - When something goes wrong
  • Audit trails - Who did what and when
  • Debug information - Details for troubleshooting

3. Traces

End-to-end request journeys through distributed systems. Traces show:

  • Request path - Which services a request flows through
  • Latency breakdown - Where time is spent
  • Dependencies - How services interact

Service Level Objectives (SLOs)

An SLO is a target for how well a service should perform. SLOs have three components:

Service Level Indicator (SLI)

A metric that measures what matters to users. Examples:

  • Availability: Percentage of successful requests
  • Latency: Percentage of requests completing within acceptable time
  • Error rate: Percentage of requests that don't fail

Service Level Objective (SLO)

The target for the SLI. Examples:

  • "99% availability" - The SLI must stay above 99%
  • "95th percentile latency under 500ms" - 95% of requests complete within 500ms
  • "99.9% success rate" - Less than 0.1% errors

Service Level Agreement (SLA)

A contractual commitment about the SLO. SLAs define what happens if we miss the SLO (refunds, credits, etc).

ℹ️ Error Budgets

If your SLO is 99% availability, you have a 1% "error budget" per month. This is how much downtime you can have before violating the SLO. Once the budget is exhausted, you must focus on stability over new features.

Graph Types in Grafana

Grafana supports several visualization types. Choose the right visualization for your data:

Graph/Time Series

Shows how a metric changes over time. Best for:

  • Trends (is latency increasing?)
  • Patterns (traffic spikes at certain times?)
  • Comparisons (two services side by side)

Gauge

Shows a single current value with min/max ranges. Best for:

  • Current SLO status (showing if we're above/below target)
  • Capacity remaining
  • Health status at a glance

Stat Panel

Shows a single large number with optional sparkline. Best for:

  • Current error rate
  • Total requests in a period
  • Key metrics that changed recently

Heatmap

Shows distribution of values across time. Best for:

  • Latency distribution (where do most requests fall?)
  • Finding outliers
  • Identifying time-dependent patterns

Table

Shows data in rows and columns. Best for:

  • Listing top errors or slow operations
  • Service health status
  • Detailed metrics that don't need visualization

Troubleshooting Tips

Dashboard shows no data?

  • Check the time range - data might be outside the selected window
  • Verify the metric name exists in Prometheus
  • Check that labels (filters) match your data
  • Test the PromQL query directly in Prometheus

Alert firing when it shouldn't?

  • Check the alert condition - is it evaluating correctly?
  • Look at the metric values in Grafana - are they at threshold?
  • Check the for: duration - alert must be true for this long
  • Review recent changes to the alert definition

PromQL query errors?

  • Check for balanced parentheses and brackets
  • Verify metric and label names are spelled correctly (case-sensitive)
  • Use Prometheus console to test basic queries first
  • Start simple, then add complexity

Metrics missing or stale?

  • Check if the component generating the metric is running
  • Verify scrape jobs are configured for that service
  • Look for errors in Prometheus targets page
  • Check application logs for export errors

Quick Reference: Common PromQL Functions

These functions appear frequently in Konflux metrics:

  • rate(metric[5m]) - Per-second change over 5 minutes (used for error rates)
  • avg_over_time(metric[1h]) - Average value over 1 hour window
  • increase(metric[1h]) - Total increase over 1 hour
  • histogram_quantile(0.95, metric) - 95th percentile (latency SLOs)
  • sum(metric) - Total across all labels
  • by(...) - Group results by labels
  • without(...) - Exclude labels from grouping
⚠️ Pro Tip: Start Monitoring Simple

When adding new metrics, start with simple queries. Complex queries are harder to debug and often hide issues. Add complexity only when you know the basics work.
